# AUR publishing

The release pipeline maintains two separate AUR packages. Each AUR Git repository receives **only `PKGBUILD` and `.SRCINFO`**, not a compiled package archive.

| AUR package | Input | Build procedure | Trigger |
| --- | --- | --- | --- |
| `fuoevolve` | GitHub release tag source archive (`archive/refs/tags/<version>.tar.gz`) | Rebuild desktop Native Image and native helpers, then stage the locally built Arch package | `release.yml`, after GitHub Release publication |
| `fuoevolve-bin` | GitHub Release asset (`FuoEvolve-<version>-linux-x64.pkg.tar.zst`) | Verify its SHA-256 and extract its installed files into makepkg's `pkgdir` | `publish-aur-bin.yml`, after the GitHub Release publishing job succeeds, even if Pages later fails |

The `-bin` workflow checks the GitHub Release publishing job separately from the Pages deployment because its `source` URL is a published release asset. `render-aur-bin-package.sh` reads the SHA-256 digest generated by GitHub for that exact asset from the release API. It fails if the asset or digest is missing rather than publishing an invalid package. `noextract` disables makepkg's default archive extraction; `package()` uses `bsdtar` to exclude upstream pacman metadata and lets makepkg regenerate it for `fuoevolve-bin`. Source and binary variants declare their mutual conflict; the binary variant provides versioned `fuoevolve`.

Both publishers clone their respective AUR Git repositories, compare the current `pkgver` with the release tag, and skip stale releases. Separate fixed GitHub Actions concurrency groups prevent overlapping publishers for the same AUR repository. The source and binary AUR repositories can update independently.

Configure GitHub Actions repository secret `AUR_SSH_PRIVATE_KEY` with a dedicated non-interactive SSH private key. Register the corresponding public key with an AUR account authorized to maintain **both** `fuoevolve` and `fuoevolve-bin`. Both AUR package names must be available to, or maintained by, that account; workflow access alone cannot create AUR ownership. No private key is committed to the repository.

Pull-request checks validate the source AUR metadata independently and test the binary metadata against the latest published release. Binary checks also download the referenced Arch asset, verify its checksum and confirm that repackaging yields an installed-files payload without the original pacman metadata. A pull-request check does not authenticate to AUR or publish a package; the first actual push needs the AUR key and maintainership configured above.

## Recover an already published release

Both three-part tags (`1.6.2`) and four-part maintenance tags (`1.6.2.1`) are supported.
If GitHub Release assets were published but an AUR publisher failed, first merge the workflow fix into `master`. Do **not** recreate or move the release tag.

- Source AUR: open **Actions → Release → Run workflow**, select `master`, set **aur_release_tag** to the existing tag. This runs source AUR publication only and skips Pages rebuilding and the release packaging matrix.
- Binary AUR: open **Actions → Publish AUR binary package → Run workflow**, select `master`, set **release_tag** to the existing tag.

The manual jobs verify that the GitHub Release is published, check the tag and existing package version, and publish only `PKGBUILD` and `.SRCINFO`. Leave **aur_release_tag** blank in a manual Release run to refresh the F-Droid repository and Pages as before.
