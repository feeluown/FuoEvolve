# AUR publishing

The release pipeline maintains two separate AUR packages. Each AUR Git repository receives **only `PKGBUILD` and `.SRCINFO`**, not a compiled package archive.

| AUR package | Input | Build procedure | Trigger |
| --- | --- | --- | --- |
| `fuoevolve` | GitHub release tag source archive (`archive/refs/tags/<version>.tar.gz`) | Rebuild desktop Native Image and native helpers, then stage the locally built Arch package | `release.yml`, after desktop release packaging |
| `fuoevolve-bin` | GitHub Release asset (`FuoEvolve-<version>-linux-x64.pkg.tar.zst`) | Verify its SHA-256 and extract its installed files into makepkg's `pkgdir` | `publish-aur-bin.yml`, after the `Release` workflow completes successfully |

The `-bin` workflow waits for GitHub Release publication because its `source` URL is a published release asset. `render-aur-bin-package.sh` reads the SHA-256 digest generated by GitHub for that exact asset from the release API. It fails if the asset or digest is missing rather than publishing an invalid package. `noextract` disables makepkg's default archive extraction; `package()` uses `bsdtar` to exclude upstream pacman metadata and lets makepkg regenerate it for `fuoevolve-bin`. Source and binary variants declare their mutual conflict; the binary variant provides versioned `fuoevolve`.

Both publishers clone their respective AUR Git repositories, compare the current `pkgver` with the release tag, and skip stale releases. Separate fixed GitHub Actions concurrency groups prevent overlapping publishers for the same AUR repository. The source and binary AUR repositories can update independently.

Configure GitHub Actions repository secret `AUR_SSH_PRIVATE_KEY` with a dedicated non-interactive SSH private key. Register the corresponding public key with an AUR account authorized to maintain **both** `fuoevolve` and `fuoevolve-bin`. Both AUR package names must be available to, or maintained by, that account; workflow access alone cannot create AUR ownership. No private key is committed to the repository.

Pull-request checks validate the source AUR metadata independently and test the binary metadata against the latest published release. Binary checks also download the referenced Arch asset, verify its checksum and confirm that repackaging yields an installed-files payload without the original pacman metadata. A pull-request check does not authenticate to AUR or publish a package; the first actual push needs the AUR key and maintainership configured above.
